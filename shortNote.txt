6] 	SONAME

	In C++, a SONAME (shared object name) is a field embedded inside a shared library (.so file) that guides the operating system's dynamic linker on which library version to load at runtime. It acts as an API/ABI management tool, ensuring backward compatibility and preventing crashes caused by mismatching library updates.	

The Three-Name Convention
When building professional C++ libraries, Linux systems track three distinct names for a single library file:
	
Name Type	Example			Purpose
Real Name	libmath.so.1.2.0	The actual file on disk containing the binary compiled code.
SONAME		libmath.so.1		Embedded inside the library and application binary. Specifies the Major API Version.
Linker Name	libmath.so		A symlink used by the compiler (g++ -lmath) to locate the library during build time.

7]	patchelf
			-> "When the loader is resolving my dependencies, look in /opt/MicroWorld/lib before the system paths."

	patchelf is a small, standalone utility used to modify existing ELF (Executable and Linkable Format) binaries and shared libraries. It is widely used by developers and system packagers (such as in the NixOS Ecosystem) to force compiled programs to look for dependencies in custom, non-standard directories without needing to recompile the source code.

	Key Capabilities
patchelf provides precise control over how the dynamic linker handles a binary's runtime dependencies:

Modify the RPATH / RUNPATH: Changes the search path embedded inside the binary where the system looks for shared libraries (.so files).
Change the Dynamic Loader / Interpreter: Directs the binary to use a specific dynamic linker (e.g., a specific version of ld-linux.so) instead of the system default.
Manage Dependencies (DT_NEEDED): Adds, removes, or replaces specific shared library dependencies declared inside the binary.
Shrink RPATH: Automatically removes paths from the RPATH that do not contain any libraries needed by the binary, reducing clutter.
Alter the SONAME: Rewrites the internal identity (SONAME) of a shared library.

10]	MIT-SHM

	MIT-SHM stands for the MIT Shared Memory Extension (also known as XShm). It is a core protocol extension for the X Window System (X11) designed to speed up the exchange of image data between an application (the X client) and the display system (the X server).

	How It Works
Traditionally, when a local application wants to draw a large image on your screen using X11, it has to pack the raw pixel data and send it to the X server over a local network socket or pipe. This serialization and data copying creates a heavy CPU bottleneck for graphic-intensive tasks. 

MIT-SHM bypasses the socket entirely. It allocates a shared memory segment (via Linux System V IPC or file descriptors) that both the application and the X server can look at simultaneously. Instead of copying a massive block of pixels, the application just writes the pixels to that shared memory pool and sends a small message telling the X server exactly where to look.

	In Linux, IPC stands for Inter-Process Communication.
Overview
	IPC is a set of programming techniques and mechanisms that allow running processes to exchange data, synchronize their execution, and share resources safely within an operating system.
Common IPC Mechanisms in Linux

    Pipes (Anonymous & Named): Used to stream data sequentially from one process to another, such as using the pipe character (|) in the terminal or FIFO files on disk.

    Message Queues: Allow processes to send and receive discrete packets of data or messages stored in a queue managed by the kernel.

    Shared Memory: The fastest IPC method, allowing multiple processes to access a single, common region of RAM directly.

    Semaphores: Used alongside shared memory to synchronize access and prevent race conditions or conflicting writes.

    Sockets (UNIX Domain & Network): Enable bidirectional data streaming between processes on the same machine or across a network.

    Signals: Lightweight notifications sent to a process to inform it that a specific event has occurred.

	ELF layout meaning


The ELF (Executable and Linkable Format) layout defines the structural architecture of a binary file used in Linux and Unix-like operating systems. It dictates how an executable program, shared library (.so), or object file (.o) is organized on disk and how the operating system loads it into system memory.
Think of it as a blueprint divided into three core parts: administrative headers, content sections (for compilers), and segments (for the OS loader).
The Structural Hierarchy of an ELF File
An ELF file has two completely different views depending on whether it is being read by a compiler/linker or executed by the operating system kernel.
text

+--------------------------------------+

|             ELF Header               |  <- File identity and blueprint
+--------------------------------------+

|      Program Header Table (PHT)      |  <- Map for Execution (Segments)
+--------------------------------------+

|             .text section            |  <- Your compiled binary code
+--------------------------------------+

|             .data section            |  <- Initialised global variables
+--------------------------------------+

|             .rodata section          |  <- Read-only strings and data
+--------------------------------------+

|             .bss section             |  <- Uninitialised variables (0)
+--------------------------------------+

|      Section Header Table (SHT)      |  <- Map for Linking (Sections)
+--------------------------------------+

Use code with caution.
The Core Components Explained
1. The ELF Header (The ID Card)
Located at the very beginning of the file, this tells the operating system how to read the binary. It contains:

    The Magic Number: A 4-byte signature (0x7f 45 4c 46 or \x7fELF) verifying it is a valid ELF file.
    Architecture Details: Specifies if it is 32-bit or 64-bit, and the CPU target (e.g., x86-64, ARM).
    The Entry Point: The exact memory address where the CPU should start executing code (usually pointing to _start, which sets up the environment before calling your main() function).

2. The Program Header Table & Segments (The Execution View)
The Program Header Table (PHT) is mandatory for executable files and shared libraries. It tells the Linux Kernel how to map the file directly into virtual memory blocks called Segments.

    PT_LOAD: Tells the kernel to load this specific chunk of code or data into RAM and assigns hardware permissions like Read, Write, or Execute (r-x or rw-).
    PT_INTERP: Specifies the path to the dynamic linker (like /lib64/ld-linux-x86-64.so.2) that must run first to handle shared libraries. (This is what patchelf alters).
    PT_DYNAMIC: Holds a list of directories and tags (like DT_NEEDED and DT_RPATH) defining what external library files this program needs to run.

3. Sections & The Section Header Table (The Linking View)
While segments are for executing, Sections are for compiling and debugging. The Section Header Table (SHT) is a index at the tail end of the file used by linkers (ld) to stitch multiple object files together.

    .text: Contains the actual compiled, read-only CPU instructions.
    .data: Contains global and static variables that have an explicit initial value (e.g., int x = 10;).
    .rodata: Stands for "Read-Only Data". Stores hardcoded string literals (e.g., cout << "Test 1: ";).
    .bss: Stores global variables that are declared but not initialised (e.g., int global_array[100];). It takes up almost zero space on disk because it just tells the system to allocate blank blocks of zeroed memory at runtime.
    .symtab / .strtab: The symbol and string tables. They store the names and positions of functions and variables, which tools like gdb use for debugging.

How to Inspect an ELF Layout on Linux
You can peer inside any compiled Linux binary using built-in command-line tools:

    View the ELF Header:
    bash

    readelf -h ./my_program

    Use code with caution.
    View the Program Headers (Segments mapped to memory):
    bash

    readelf -l ./my_program

    Use code with caution.
    View individual Sections (Code, data sizes):
    bash

    readelf -S ./my_program

    Use code with caution.


14] 	Diff between NULL and nullptr

	In C++, both NULL and nullptr are used to represent a pointer that doesn't point to any memory location, but they are handled completely differently by the compiler.
The core difference is that NULL is an integer, whereas nullptr is a true pointer type.

Direct Comparison Overview
Feature	NULL	nullptr
Introduced In	C (inherited by C++)	C++11 (Modern C++)
Underlying Type	int (value 0) or 0L	std::nullptr_t (a distinct pointer type)
Type Safety	Poor. Can be implicitly converted to integers.	Excellent. Can only be converted to pointer types.
Function Overloading	Prone to ambiguity and matching int parameters.	Safely matches pointer parameters exclusively.
Why NULL Can Cause Bugs (The Function Overloading Problem)
Because NULL evaluates directly to the number 0, it can trick the compiler into calling an integer function instead of a pointer function when you overload them.
The Bug with NULL:
cpp

#include <iostream>

void check(int x) {
    std::cout << "Called integer function\n";
}

void check(int* ptr) {
    std::cout << "Called pointer function\n";
}

int main() {
    // You want to pass a null pointer, but NULL is 0
    check(NULL); 
    
    // Output: "Called integer function" 
    // This is a subtle bug!
}

Use code with caution.
The Fix with nullptr:
cpp

int main() {
    // nullptr knows it is a pointer
    check(nullptr); 
    
    // Output: "Called pointer function"
    // Behaves exactly as intended.
}

	C++ String vs C‑String (char array) – Complete Guide for 5+ YOE Developer

As a senior C++ engineer, choosing between std::string and C‑style char[] is a design decision based on performance, safety, interoperability, and memory characteristics. Below is a comprehensive guide with examples.
📌 1. Quick Decision Table
Scenario	Use std::string	Use C‑String (char[])
General-purpose string handling	✅ Yes	❌ No
Dynamic size / resizing	✅ Yes	❌ No
Safety & exception handling	✅ Yes	❌ No
Interfacing with C APIs	⚠️ Use .c_str()	✅ Yes
Fixed-size buffers (embedded)	❌ No	✅ Yes
Performance-critical, no allocation	❌ No	✅ Yes
Binary data (not text)	❌ No (use vector<char>)	✅ Yes
Compile-time known size	std::array<char, N>	✅ Yes
Large text processing	✅ Yes	❌ No
📌 2. std::string – When and Why
Characteristics

    Dynamic – grows/shrinks automatically.

    Safe – bounds-checked (at()), RAII memory management.

    Rich API – find, substr, replace, append, etc.

    Exception-safe – throws std::bad_alloc on failure.

    O(1) size – stores length internally.

Example 1: General Text Handling
cpp

#include <iostream>
#include <string>
using namespace std;

int main()
{
    string name = "Rushikesh";
    string greeting = "Hello, " + name + "!";
    
    greeting += " Welcome to C++.";
    
    cout << greeting << "\n";
    cout << "Length: " << greeting.length() << "\n";
    cout << "Substring: " << greeting.substr(7, 9) << "\n";
    
    if (greeting.find("C++") != string::npos)
        cout << "Found C++\n";
    
    return 0;
}

Output:
text

Hello, Rushikesh! Welcome to C++.
Length: 31
Substring: Rushikesh
Found C++

Why std::string?

    Automatic memory management.

    Easy concatenation (+, +=).

    No manual strlen, strcpy, strcat.

Example 2: Dynamic Input

Characteristics

    Fixed size – known at compile-time (or dynamically allocated).

    No overhead – just a pointer to bytes.

    Fast – no allocation, no ref counting.

    Low-level – direct memory access.

    Dangerous – buffer overflows, no bounds checking.

	🎯 FILE* vs std::fstream — When to Use Which

There are two different I/O families:

C API
│
├── FILE*
├── fopen()
├── fread()
├── fwrite()
├── fprintf()
├── fscanf()
└── fclose()

C++ API
│
├── std::ifstream   → reading
├── std::ofstream   → writing
├── std::fstream    → reading + writing
└── RAII automatic close

1. FILE *fp = fopen(...)

This is the C standard library file API.

#include <cstdio>

FILE *fp = fopen("data.txt", "r");

You must explicitly close it:

fclose(fp);

Basic pattern:

FILE *fp = fopen("data.txt", "r");

if(fp == nullptr)
{
    perror("fopen");
    return 1;
}

/* use file */

fclose(fp);

2. Why would you use FILE* in C++?

The biggest reason is C API compatibility.

Suppose an existing Linux/C library gives you:

FILE *fp;

or expects:

void processFile(FILE *fp);

Then using FILE* is natural.

For example:

FILE *fp = fopen("/tmp/test.txt", "r");

if(fp == nullptr)
{
    perror("fopen");
    return 1;
}

char buffer[1024];

while(fgets(buffer, sizeof(buffer), fp) != nullptr)
{
    printf("%s", buffer);
}

fclose(fp);

3. FILE* is especially common in legacy C/Linux code

In a large Linux codebase, you may encounter:

FILE *fp;
fopen();
fgets();
fprintf();
fread();
fwrite();
fclose();

For example:

FILE *fp = fopen("/var/log/application.log", "a");

if(fp != nullptr)
{
    fprintf(fp, "Application started\n");

    fclose(fp);
}

If you're maintaining an existing C/C++ Linux project that already uses this API extensively, continuing with it can make sense.
4. std::ofstream

For normal C++ file writing, I would generally prefer:

#include <fstream>

std::ofstream outFile(filePath);

Example:

#include <fstream>
#include <iostream>
#include <string>

int main()
{
    std::string filePath = "/tmp/test.txt";

    std::ofstream outFile(filePath);

    if(!outFile)
    {
        std::cerr << "Failed to open file\n";
        return 1;
    }

    outFile << "Hello Linux\n";
    outFile << "C++ Programming\n";

    return 0;
}

Notice:

outFile.close();

is not required here.

Why?

Because ofstream follows RAII.

When outFile goes out of scope:

outFile destroyed
       ↓
ofstream destructor
       ↓
file closed

5. std::ifstream

For normal C++ file reading:

std::ifstream inFile(filePath);

Example:

#include <fstream>
#include <iostream>
#include <string>

int main()
{
    std::string filePath = "/tmp/test.txt";

    std::ifstream inFile(filePath);

    if(!inFile)
    {
        std::cerr << "Failed to open file\n";
        return 1;
    }

    std::string line;

    while(std::getline(inFile, line))
    {
        std::cout << line << '\n';
    }

    return 0;
}

Again, you normally don't need:

inFile.close();

The destructor closes it automatically.
6. Why RAII matters in an interview

Consider:

void readFile()
{
    std::ifstream inFile("/tmp/test.txt");

    if(!inFile)
    {
        return;
    }

    // process file

    return;
}

Even though we return early:

return
 ↓
inFile destructor
 ↓
file automatically closed

This is one of the major advantages of C++ streams.

With FILE*, you need to be careful:

void readFile()
{
    FILE *fp = fopen("/tmp/test.txt", "r");

    if(fp == nullptr)
    {
        return;
    }

    // process file

    fclose(fp);
}

And if your function has multiple return paths, exceptions, or complex ownership, manually managing fclose() becomes more error-prone.
7. std::fstream

If you need both reading and writing:

std::fstream file;

Example:

#include <fstream>

std::fstream file(
    "/tmp/test.txt",
    std::ios::in | std::ios::out
);

Then:

file << "Hello";

std::string line;

std::getline(file, line);

16. Important buffering difference

FILE* uses C stdio buffering.

For example:

fprintf(fp, "Hello\n");

doesn't necessarily mean the bytes immediately reach the disk/device.

Similarly, C++ streams have buffering layers too.

And Linux itself has filesystem/page-cache behavior.

So:

Your C++ code
     ↓
iostream / stdio buffering
     ↓
system call
     ↓
Linux kernel
     ↓
page cache / filesystem
     ↓
storage

This matters when you're discussing performance or durability.
17. Very important interview trap: flush() ≠ fsync()

This is a strong Linux interview point.

outFile.flush();

flushes the C++ stream's buffer.

It does not mean:

    "The data is physically persistent on disk."

For durability, Linux provides:

fsync(fd);

There are additional details around filesystem/device behavior, but the key distinction is:

flush()
    ↓
user-space stream buffering

fsync()
    ↓
request synchronization through the kernel

Don't claim that flush() guarantees physical persistence.

For low-level Linux descriptor operations → use POSIX file descriptors.

As a senior C++ engineer, you'll encounter both C‑style file I/O (fopen/fclose) and C++ streams (std::ifstream/std::ofstream). The choice depends on interoperability, performance, safety, and context (application code vs. system programming).
📌 1. Quick Decision Table
Scenario	Use FILE*	Use std::fstream
C++ application code	❌ No	✅ Yes
Linux system programming	✅ Yes	❌ No
Interfacing with C libraries	✅ Yes	❌ No
Type-safe I/O	❌ No	✅ Yes
RAII automatic cleanup	❌ No (manual fclose)	✅ Yes
Binary I/O (read/write)	✅ Yes	✅ Yes
Formatted input/output	✅ Yes (fprintf/fscanf)	✅ Yes (<<, >>)
Performance-critical	✅ Slightly faster	Slightly slower
Exception safety	❌ Manual	✅ Exceptions
Kernel module / driver	✅ Yes	❌ Not available
📌 2. When to Use FILE* (fopen / fclose)
✅ Use When:
1. Interfacing with C libraries

Many C libraries use FILE* (e.g., libpng, zlib, libcurl in some modes).
cpp

#include <cstdio>
#include <zlib.h>

int main()
{
    FILE* fp = fopen("data.gz", "rb");
    if (!fp) return 1;
    
    gzFile gz = gzdopen(fileno(fp), "rb");  // needs FILE*
    // ...
    
    fclose(fp);
    return 0;
}

2. Linux system programming / POSIX APIs

Some POSIX functions return FILE* (e.g., popen, fdopen).
cpp

#include <cstdio>
#include <cstdlib>

int main()
{
    // popen requires FILE*
    FILE* fp = popen("ls -l", "r");
    if (!fp) return 1;
    
    char buf[256];
    while (fgets(buf, sizeof(buf), fp))
        printf("%s", buf);
    
    pclose(fp);
    return 0;
}

3. Simple, low-level file I/O

When you need precise control over buffering and don't want C++ overhead.
cpp

#include <cstdio>

int main()
{
    FILE* fp = fopen("/tmp/data.bin", "wb");
    if (!fp) return 1;
    
    int data[5] = {1, 2, 3, 4, 5};
    fwrite(data, sizeof(int), 5, fp);
    
    fclose(fp);
    return 0;
}

4. snprintf / fprintf for formatting

When you need C‑style formatting without std::ostringstream.
cpp

#include <cstdio>

int main()
{
    char buf[64];
    snprintf(buf, sizeof(buf), "PID: %d, Name: %s", 1234, "process");
    printf("%s\n", buf);
    return 0;
}

5. Kernel modules / embedded systems

C++ streams may not be available in kernel space or bare‑metal.
c

// Kernel module code
struct file* fp = filp_open("/tmp/log", O_WRONLY | O_CREAT, 0644);
if (!IS_ERR(fp))
{
    kernel_write(fp, "hello\n", 6, &pos);
    filp_close(fp, NULL);
}

❌ Don't Use FILE* When:

    Writing new C++ application code.

    You want RAII / automatic cleanup.

    You need type safety and exceptions.

    You're doing formatted I/O in C++.

📌 3. When to Use std::ifstream / std::ofstream
✅ Use When:
1. General C++ application code

Idiomatic C++ with RAII and exception handling.
cpp

#include <fstream>
#include <iostream>
using namespace std;

int main()
{
    // Writing
    {
        ofstream outFile("/tmp/data.txt");
        if (!outFile)
        {
            cerr << "Failed to open file\n";
            return 1;
        }
        outFile << "Hello, World!\n";
        outFile << "Value: " << 42 << "\n";
    }   // automatically closed here (RAII)
    
    // Reading
    {
        ifstream inFile("/tmp/data.txt");
        string line;
        while (getline(inFile, line))
            cout << line << "\n";
    }
    
    return 0;
}

2. Type-safe formatted I/O

<< and >> operators handle types automatically.
cpp

#include <fstream>
#include <string>
using namespace std;

int main()
{
    ofstream out("config.txt");
    
    string name = "Rushikesh";
    int age = 25;
    double salary = 50000.50;
    
    out << name << "\n";
    out << age << "\n";
    out << salary << "\n";
    
    // Read back
    ifstream in("config.txt");
    in >> name >> age >> salary;
    
    return 0;
}

3. RAII – Automatic cleanup

No need to call close() manually – destructor handles it.
cpp

#include <fstream>
#include <stdexcept>

void writeData(const std::string& path)
{
    std::ofstream out(path);
    if (!out)
        throw std::runtime_error("Cannot open file");
    
    out << "data\n";
    // No fclose needed
}

4. Exception-safe file handling

Enable exceptions for automatic error propagation.
cpp

#include <fstream>
#include <iostream>

int main()
{
    try
    {
        std::ifstream in;
        in.exceptions(std::ifstream::failbit | std::ifstream::badbit);
        in.open("/tmp/nonexistent.txt");
        
        std::string line;
        std::getline(in, line);
    }
    catch (const std::ios_base::failure& e)
    {
        std::cerr << "I/O error: " << e.what() << "\n";
    }
    
    return 0;
}

5. Working with std::string

No need to convert to char*.
cpp

#include <fstream>
#include <string>

int main()
{
    std::string filename = "/tmp/data.txt";
    std::ofstream out(filename);   // takes std::string directly
    
    std::string content = "Hello";
    out << content;
    
    return 0;
}

📌 5. Binary I/O Comparison
FILE* Binary I/O
cpp

#include <cstdio>

struct Data
{
    int id;
    double value;
};

int main()
{
    Data d = {42, 3.14};
    
    // Write
    FILE* fp = fopen("/tmp/data.bin", "wb");
    fwrite(&d, sizeof(Data), 1, fp);
    fclose(fp);
    
    // Read
    Data d2;
    fp = fopen("/tmp/data.bin", "rb");
    fread(&d2, sizeof(Data), 1, fp);
    fclose(fp);
    
    printf("id=%d, value=%f\n", d2.id, d2.value);
    return 0;
}

std::ofstream Binary I/O
cpp

#include <fstream>
#include <iostream>

struct Data
{
    int id;
    double value;
};

int main()
{
    Data d = {42, 3.14};
    
    // Write
    std::ofstream out("/tmp/data.bin", std::ios::binary);
    out.write(reinterpret_cast<const char*>(&d), sizeof(Data));
    out.close();
    
    // Read
    Data d2;
    std::ifstream in("/tmp/data.bin", std::ios::binary);
    in.read(reinterpret_cast<char*>(&d2), sizeof(Data));
    in.close();
    
    std::cout << "id=" << d2.id << ", value=" << d2.value << "\n";
    return 0;
}

📌 6. When to Mix Both (FILE* ↔ fstream)

Sometimes you need to convert:
FILE* → std::fstream

Not directly possible, but you can use fdopen + gnu_cxx::stdio_filebuf (GCC extension).
cpp

#include <fstream>
#include <cstdio>
#include <ext/stdio_filebuf.h>

int main()
{
    FILE* fp = fopen("/tmp/data.txt", "w");
    __gnu_cxx::stdio_filebuf<char> filebuf(fileno(fp), std::ios::out);
    std::ostream out(&filebuf);
    
    out << "Hello\n";
    out.flush();
    
    fclose(fp);
    return 0;
}

std::fstream → FILE*

Not directly possible, but you can use FILE* to open then wrap with std::ifstream.
📌 7. Performance Comparison
cpp

#include <chrono>
#include <cstdio>
#include <fstream>
#include <iostream>

using namespace std;
using namespace std::chrono;

int main()
{
    const int N = 100000;
    
    // FILE*
    auto start = high_resolution_clock::now();
    {
        FILE* fp = fopen("/tmp/c_style.txt", "w");
        for (int i = 0; i < N; i++)
            fprintf(fp, "Line %d\n", i);
        fclose(fp);
    }
    auto end = high_resolution_clock::now();
    auto c_time = duration_cast<milliseconds>(end - start).count();
    
    // std::ofstream
    start = high_resolution_clock::now();
    {
        std::ofstream out("/tmp/cpp_style.txt");
        for (int i = 0; i < N; i++)
            out << "Line " << i << "\n";
    }
    end = high_resolution_clock::now();
    auto cpp_time = duration_cast<milliseconds>(end - start).count();
    
    cout << "FILE*:        " << c_time << " ms\n";
    cout << "ofstream:     " << cpp_time << " ms\n";
    
    return 0;
}

Typical output:
text

FILE*:        35 ms
ofstream:     42 ms

Conclusion: FILE* is slightly faster (no virtual dispatch, no locale overhead), but std::ofstream is safer and more idiomatic.

📌 10. Interview Pitch (30 seconds)

    "I use std::ofstream/std::ifstream for general C++ application code because they provide RAII, type safety, and exception handling. I use FILE* when interfacing with C libraries (like zlib, popen) or POSIX APIs that return FILE*, and in performance-critical or embedded contexts where C++ streams aren't available or add overhead. In modern C++, std::fstream is the default choice; FILE* is reserved for C interop and system programming."
