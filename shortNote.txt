CXXFLAGS := -fPIC -Wall -Wextra -std=c++17 -gdwarf-2
LDFLAGS  := -lstdc++fs

CXXFLAGS → passed to the compiler during compilation

LDFLAGS → passed to the linker during linking

-fPIC generates position-independent code, essential for building shared libraries (.so files) that can be loaded at any memory address.

	Makes code relocatable for shared libraries

-Wall -Wextra	Enables all warnings

-std=c++17	Uses C++17 features

-gdwarf-2	Adds debug info

-lstdc++fs links the filesystem library 

Q: Difference between CXXFLAGS and LDFLAGS?

    A: CXXFLAGS is for compilation (syntax, warnings, standard). LDFLAGS is for linking (library paths, libraries). Putting -lstdc++fs in CXXFLAGS fails because the linker never sees it.

6] 	SONAME

	In C++, a SONAME (shared object name) is a field embedded inside a shared library (.so file) that guides the operating system's dynamic linker on which library version to load at runtime. It acts as an API/ABI management tool, ensuring backward compatibility and preventing crashes caused by mismatching library updates.	

The Three-Name Convention
When building professional C++ libraries, Linux systems track three distinct names for a single library file:
	
Name Type	Example			Purpose
Real Name	libmath.so.1.2.0	The actual file on disk containing the binary compiled code.
SONAME		libmath.so.1		Embedded inside the library and application binary. Specifies the Major API Version.
Linker Name	libmath.so		A symlink used by the compiler (g++ -lmath) to locate the library during build time.

7]	patchelf
			-> "When the loader is resolving my dependencies, look in /opt/MicroWorld/lib before the system paths."

	patchelf is a small, standalone utility used to modify existing ELF (Executable and Linkable Format) binaries and shared libraries. It is widely used by developers and system packagers (such as in the NixOS Ecosystem) to force compiled programs to look for dependencies in custom, non-standard directories without needing to recompile the source code.

	Key Capabilities
patchelf provides precise control over how the dynamic linker handles a binary's runtime dependencies:

Modify the RPATH / RUNPATH: Changes the search path embedded inside the binary where the system looks for shared libraries (.so files).
Change the Dynamic Loader / Interpreter: Directs the binary to use a specific dynamic linker (e.g., a specific version of ld-linux.so) instead of the system default.
Manage Dependencies (DT_NEEDED): Adds, removes, or replaces specific shared library dependencies declared inside the binary.
Shrink RPATH: Automatically removes paths from the RPATH that do not contain any libraries needed by the binary, reducing clutter.
Alter the SONAME: Rewrites the internal identity (SONAME) of a shared library.

	
	for f in /opt/MicroWorld/lib*.so*; do
	    [ -f "$f" ] && patchelf --set-rpath /opt/MicroWorld/lib "$f"
	done

	Tools to Inspect Memory
1. /proc/<pid>/maps
bash

cat /proc/$$/maps

Shows segments: text, data, heap, stack, shared libs.
2. pmap
bash

pmap -x <pid>

Shows memory usage per segment.
3. valgrind
bash

valgrind --leak-check=full ./program

Detects leaks, invalid access, uninitialized reads.
4. gdb
bash

gdb ./program
(gdb) break main
(gdb) run
(gdb) info proc mappings

Shows memory layout during debugging.
5. size command
bash

size a.out

Shows sizes of text, data, bss sections.

Example:
text

   text    data     bss     dec     hex filename
   1534     600       8    2142     85e a.out	

10]	MIT-SHM

	MIT-SHM stands for the MIT Shared Memory Extension (also known as XShm). It is a core protocol extension for the X Window System (X11) designed to speed up the exchange of image data between an application (the X client) and the display system (the X server).

	How It Works
Traditionally, when a local application wants to draw a large image on your screen using X11, it has to pack the raw pixel data and send it to the X server over a local network socket or pipe. This serialization and data copying creates a heavy CPU bottleneck for graphic-intensive tasks. 

MIT-SHM bypasses the socket entirely. It allocates a shared memory segment (via Linux System V IPC or file descriptors) that both the application and the X server can look at simultaneously. Instead of copying a massive block of pixels, the application just writes the pixels to that shared memory pool and sends a small message telling the X server exactly where to look.

	In Linux, IPC stands for Inter-Process Communication.
Overview
	IPC is a set of programming techniques and mechanisms that allow running processes to exchange data, synchronize their execution, and share resources safely within an operating system.
Common IPC Mechanisms in Linux

    Pipes (Anonymous & Named): Used to stream data sequentially from one process to another, such as using the pipe character (|) in the terminal or FIFO files on disk.

    Message Queues: Allow processes to send and receive discrete packets of data or messages stored in a queue managed by the kernel.

    Shared Memory: The fastest IPC method, allowing multiple processes to access a single, common region of RAM directly.

    Semaphores: Used alongside shared memory to synchronize access and prevent race conditions or conflicting writes.

    Sockets (UNIX Domain & Network): Enable bidirectional data streaming between processes on the same machine or across a network.

    Signals: Lightweight notifications sent to a process to inform it that a specific event has occurred.

	ELF layout meaning


The ELF (Executable and Linkable Format) layout defines the structural architecture of a binary file used in Linux and Unix-like operating systems. It dictates how an executable program, shared library (.so), or object file (.o) is organized on disk and how the operating system loads it into system memory.
Think of it as a blueprint divided into three core parts: administrative headers, content sections (for compilers), and segments (for the OS loader).
The Structural Hierarchy of an ELF File
An ELF file has two completely different views depending on whether it is being read by a compiler/linker or executed by the operating system kernel.
text

+--------------------------------------+

|             ELF Header               |  <- File identity and blueprint
+--------------------------------------+

|      Program Header Table (PHT)      |  <- Map for Execution (Segments)
+--------------------------------------+

|             .text section            |  <- Your compiled binary code
+--------------------------------------+

|             .data section            |  <- Initialised global variables
+--------------------------------------+

|             .rodata section          |  <- Read-only strings and data
+--------------------------------------+

|             .bss section             |  <- Uninitialised variables (0)
+--------------------------------------+

|      Section Header Table (SHT)      |  <- Map for Linking (Sections)
+--------------------------------------+

Use code with caution.
The Core Components Explained
1. The ELF Header (The ID Card)
Located at the very beginning of the file, this tells the operating system how to read the binary. It contains:

    The Magic Number: A 4-byte signature (0x7f 45 4c 46 or \x7fELF) verifying it is a valid ELF file.
    Architecture Details: Specifies if it is 32-bit or 64-bit, and the CPU target (e.g., x86-64, ARM).
    The Entry Point: The exact memory address where the CPU should start executing code (usually pointing to _start, which sets up the environment before calling your main() function).

2. The Program Header Table & Segments (The Execution View)
The Program Header Table (PHT) is mandatory for executable files and shared libraries. It tells the Linux Kernel how to map the file directly into virtual memory blocks called Segments.

    PT_LOAD: Tells the kernel to load this specific chunk of code or data into RAM and assigns hardware permissions like Read, Write, or Execute (r-x or rw-).
    PT_INTERP: Specifies the path to the dynamic linker (like /lib64/ld-linux-x86-64.so.2) that must run first to handle shared libraries. (This is what patchelf alters).
    PT_DYNAMIC: Holds a list of directories and tags (like DT_NEEDED and DT_RPATH) defining what external library files this program needs to run.

3. Sections & The Section Header Table (The Linking View)
While segments are for executing, Sections are for compiling and debugging. The Section Header Table (SHT) is a index at the tail end of the file used by linkers (ld) to stitch multiple object files together.

    .text: Contains the actual compiled, read-only CPU instructions.
    .data: Contains global and static variables that have an explicit initial value (e.g., int x = 10;).
    .rodata: Stands for "Read-Only Data". Stores hardcoded string literals (e.g., cout << "Test 1: ";).
    .bss: Stores global variables that are declared but not initialised (e.g., int global_array[100];). It takes up almost zero space on disk because it just tells the system to allocate blank blocks of zeroed memory at runtime.
    .symtab / .strtab: The symbol and string tables. They store the names and positions of functions and variables, which tools like gdb use for debugging.

How to Inspect an ELF Layout on Linux
You can peer inside any compiled Linux binary using built-in command-line tools:

    View the ELF Header:
    bash

    readelf -h ./my_program

    Use code with caution.
    View the Program Headers (Segments mapped to memory):
    bash

    readelf -l ./my_program

    Use code with caution.
    View individual Sections (Code, data sizes):
    bash

    readelf -S ./my_program

    Use code with caution.
